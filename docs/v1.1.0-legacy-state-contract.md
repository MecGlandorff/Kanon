# Kanon v1.0.0 Legacy State Contract

This Phase 0 characterization freezes the supported
`.kanon/STATE.json` boundary that v1.1.0 must retain while replacing the
legacy compatibility runtime. It describes the immutable `v1.0.0` tag at
commit `21c6d1df2cd2676354a9de6bab96e4651781a608`; the relevant source files are
byte-identical at the start of the refactor branch.

This inventory is deliberately limited to the repository-local state
checkpoint. Successful `.kanon/TODO.md` and refresh-output behavior is recorded
in `docs/v1.1.0-compatibility-write-success-contract.md`. Configuration,
external receipt and handoff stores, stable result schemas, rejected writes,
and diagnostic vocabularies remain separate Phase 0 work.

## Public consumers

Two reader paths consume the same file with different purposes.

| Public workflows | Reader behavior | Default input bound |
| --- | --- | ---: |
| `refresh` | Parses and validates schema 1 or schema 2 before using prior state to render continuity output. A malformed regular file is ignored with a warning before the new valid checkpoint is written; an unsafe write target still fails closed. | 2 MiB, configurable from 1 KiB through 8 MiB |
| `resume`, `verify`, `steer` | Parses the file and projects only bounded continuity fields before comparing them with authoritative live evidence. Invalid projected state becomes an `Unknown` checkpoint and the read-only command continues. | Fixed 2 MiB |

`orient`, `brief`, `ask`, `status`, `aswitch`, and `todo` do not directly read
`STATE.json`. The stable readers do not call the compatibility validator; the
replacement architecture must account for this split rather than assuming
that one existing reader already defines all behavior.

Both paths distinguish a missing checkpoint from unavailable or invalid input.
Their contained reads reject malformed, oversized, unreadable, linked,
outside-root, or otherwise unsafe state. Repository state is data only and is
never executed.

## Historical schema 1 adapter

The compatibility validator interprets a missing `schema_version` as version
1. An explicit integer value of `1` has the same meaning. The accepted shape
is intentionally narrow in requirements and broad in historical tolerance:

- the root and `repo` values must be ordinary, non-array data objects;
- top-level proxies or accessor properties and accessor-bearing `repo` objects
  are rejected without invoking user-defined code;
- `repo` has no required child fields under the schema-1 validator;
- all other historical fields and unknown keys are accepted without
  validation; and
- a successful disk read returns those fields with `schema_version: 1` added
  when it was absent.

This permissive adapter is supported compatibility behavior. A narrow v1.1.0
adapter may discard fields it does not use internally, but it must continue to
read valid versionless and explicit-version-1 checkpoints without executing
or trusting their content.

For stable continuity comparisons, historical state is useful when `repo.root`
is a safe absolute path. Optional `generated_at`, `files`, `scan`, `git`, and
`purpose` values are validated when present; a malformed value makes the prior
checkpoint `Unknown`. Malformed `verification` issue entries are discarded
instead of invalidating the checkpoint. Unknown fields are ignored. Omitting
optional comparison data is valid but leaves the corresponding comparisons
unavailable.

## Current schema 2

`refresh` writes `schema_version: 2`. The compatibility validator rejects
versions below 1 or above 2, non-integer versions, missing required version-2
fields, unknown version-2 fields, invalid timestamps, and invalid nested
values.

The exact required top-level schema is:

| Field | Required value |
| --- | --- |
| `schema_version` | Integer `2` |
| `version`, `run_id` | Strings |
| `generated_at` | String accepted by `Date.parse` |
| `repo`, `scan`, `git`, `purpose`, `commands`, `code_intelligence`, `tests`, `ci`, `deployment`, `release`, `current_state`, `verification`, `configuration`, `command_execution`, `files` | Exact nested objects |
| `important_files`, `todos` | Exact arrays of validated records |
| `evidence_count` | Nonnegative integer |

Nested records reject unknown keys. Their complete field definitions and
scalar constraints are centralized in `src/persistence/state-fields.js`.
Notable enums are confidence `known | likely | unknown`, command policy
`ask | never`, and nullable lowercase SHA-256 file fingerprints. This is the
only state version emitted at v1.0.0; snapshot JSON files contain the same
validated state object.

The stable continuity readers deliberately do not use `schema_version` as
their gate. They accept a prior object only when the bounded continuity
projection is valid. This observed implementation detail must not be mistaken
for a promise that future checkpoint schema numbers are supported; any
consolidation must preserve valid schema-1 and schema-2 meaning and explicitly
characterize malformed or future-version handling before changing it.

## Persistence and failure behavior

- `refresh` writes `STATE.json` and its optional snapshot with a trailing
  newline through atomic, same-directory, contained writes.
- A missing prior file is valid absence. A malformed, over-budget, or rejected
  prior read produces no state object and a bounded warning. Stable reads
  continue; `refresh` continues past read validation but still refuses an
  unsafe destination when writing the replacement.
- Stable consumers are read-only and leave every repository byte unchanged.
- Link, traversal, replacement-race, read-budget, plain-object, proxy, and
  accessor defenses remain part of the contract. A small compatibility
  adapter may not bypass the existing contained-read primitives.

## Evidence and reproduction

The schema-1 normalization assertions live in `test/kanon.test.js`. The stable
versionless checkpoint comparison is fixed in `test/v1-skills.test.js`;
malformed, oversized, linked, proxy, accessor, and read-only cases remain in
`test/v1-continuity.test.js`, `test/v1-skills-adversarial.test.js`, and
`test/staff.test.js`.

After inspecting the invoked definitions, reproduce this characterization
with:

```sh
git diff --exit-code v1.0.0 -- \
  src/version.js src/persistence/state.js \
  src/persistence/state-fields.js src/continuity/engine.js \
  src/v1/repository/inspect.js

node --test \
  test/kanon.test.js \
  test/v1-continuity.test.js \
  test/v1-skills.test.js \
  test/v1-skills-adversarial.test.js \
  test/staff.test.js
```
