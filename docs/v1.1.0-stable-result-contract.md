# Kanon v1.0.0 Stable Result Contract

This Phase 0 inventory freezes the machine-readable result boundary shared by
the stable and compatibility-read workflows that v1.1.0 must preserve. It
describes the immutable `v1.0.0` tag at commit
`21c6d1df2cd2676354a9de6bab96e4651781a608`; the canonical source and generated
runtime copy were byte-identical at the start of this inventory.

This document covers the common stable envelope, its status namespaces,
deprecation subresult, and diagnostic aggregation. The full nested report
shapes remain defined by their individual implementations and tests. The
legacy `refresh` and `todo` text/JSON results are a separate compatibility
boundary.

## Common JSON envelope

Every stable/read workflow that reaches stable invocation in JSON mode returns
one object with schema `kanon-stable-skill-result-v1` and these exact top-level
fields:

| Field | Contract |
| --- | --- |
| `schema` | Literal `kanon-stable-skill-result-v1`. |
| `version` | Installed package version reported by the deprecation result, or `Unknown` when that version is unavailable. |
| `skill` | `orient`, `resume`, `verify`, `status`, `steer`, `aswitch`, or `Unknown` for an invalid invocation. Compatibility aliases report their routed stable skill. |
| `ok` | Exactly the nested report's `ok`; it is not process-exit status and is not changed by registry availability or deprecation. |
| `status` | The nested report status normalized to `Known`, `Stale`, or `Unknown`. No other top-level status is emitted. |
| `host` | The fixed notice-mode host capability object below. |
| `deprecation` | The independently evaluated exact-version deprecation result. |
| `report` | The selected stable report or the invalid-invocation report. |
| `diagnostics` | The bounded aggregate described below. |

The host object has exactly these values apart from its three-way `name`:

```json
{
  "name": "codex-cli | claude-code | Unknown",
  "mode": "notice",
  "enforcement": false,
  "hook_status": "Unknown",
  "lifecycle_notice_hook": "Unavailable",
  "notice_delivery": "explicit-skill-and-status-output"
}
```

The report discriminant is selected as follows:

| Routed skill | `report.schema` |
| --- | --- |
| `orient` | `kanon-orient-report-v1` |
| `resume` | `kanon-resume-report-v1` |
| `verify` | `kanon-verify-report-v1` |
| `status` | `kanon-status-report-v1` |
| `steer` | `kanon-steer-report-v1` |
| `aswitch` | `kanon-aswitch-report-v1` |
| Invalid invocation | `kanon-invalid-invocation-v1` |

An invalid invocation still performs the deprecation check, then returns
`skill: "Unknown"`, `ok: false`, and `status: "Unknown"`. Its report is:

```json
{
  "schema": "kanon-invalid-invocation-v1",
  "ok": false,
  "status": "Unknown",
  "enforcement": false,
  "diagnostic": "Stable skill invocation input was unavailable or invalid.",
  "diagnostics": []
}
```

## Status namespaces

The envelope status vocabulary is only `Known`, `Stale`, and `Unknown`.
`Suggested` can occur in nested advisory values, but is never an envelope
status. Other nested components use distinct vocabularies and must not be
collapsed into the envelope namespace. In particular:

- deprecation uses `Current`, `Deprecated`, or `Unknown`;
- receipt freshness and handoff classifications can use their own values;
- host lifecycle state remains the explicit `Unknown`/`Unavailable` pair;
- `ok` remains a boolean result flag, not a fourth evidence status.

The envelope status reflects the selected skill report only. A successful
`Known` skill report can therefore coexist with an `Unknown` deprecation
subresult when the registry is offline. Conversely, deprecation does not turn a
skill result into `Stale` or make `ok` false.

## Deprecation subresult

Every stable invocation consults the bundled exact package version before
dispatch, including malformed invocations. The `deprecation` field is one of
three tagged shapes:

| Status | Required result fields beyond `ok`, `status`, and `diagnostics` |
| --- | --- |
| `Current` | `package_name`, `installed_version`, `checked_at`, and `cache` |
| `Deprecated` | Current fields plus sanitized `reason` and rendered `warning` |
| `Unknown` | A primary `diagnostic`; `package_name` and `installed_version` are present only when known |

`cache` is `hit`, `updated`, or `unavailable`. A `Deprecated` warning is printed
before ordinary text output, but the deprecation subtree otherwise remains
separate from the skill report. An `Unknown` lookup can still supply the known
installed version to the outer `version` field.

The v1.0 default registry behavior is part of this contract. Making it opt-in
or changing when it runs requires the separate human product decision called
out in the refactor plan.

## Diagnostic contract

Reports and deprecation results each carry a plural `diagnostics` array.
The envelope constructs its array by:

1. taking report diagnostics first and deprecation diagnostics second;
2. removing exact duplicate input values while preserving first occurrence;
3. sanitizing each item to at most 512 UTF-8 bytes;
4. dropping empty values; and
5. returning at most 16 items.

A branch's singular primary `diagnostic` stays inside that branch. It is not
automatically promoted into the envelope array. In particular, an `Unknown`
deprecation result's primary diagnostic must be read from `deprecation`; it is
not necessarily repeated at the top level.

Diagnostics are bounded human-readable explanations, not stable diagnostic
codes. Consumers should branch on schema, `ok`, and the applicable status
field rather than parsing diagnostic prose. Repository-derived control and
display-confusion characters remain subject to the existing sanitization
boundary.

## Text rendering

Default text output uses the envelope's skill, status, and host in a fixed
notice-mode heading. The fenced, explicitly untrusted JSON block contains the
nested `report`, not the full envelope. Only a `Deprecated` result adds its
warning ahead of that heading. Semantic `Stale` and `Unknown` results remain
normal exit-code-zero output; thrown CLI/input failures retain the separate
exit meanings recorded in `docs/v1.1.0-public-cli-contract.md`.

## Evidence and reproduction

The boundary is defined by `src/v1/skills/invoke.js`,
`src/v1/registry/deprecation.js`, `src/v1/cli.js`, and the six files below
`src/v1/skills/`. The generated copies under `runtime/` are package artifacts,
not a second contract definition.

Confirm that the implementation remains identical to the immutable release
tag and run the focused characterization after inspecting the commands:

```sh
git diff --exit-code v1.0.0 -- src/v1 runtime skills

node --test \
  --test-name-pattern="stable results preserve one exact envelope and bounded vocabulary" \
  test/v1-skills.test.js
```
